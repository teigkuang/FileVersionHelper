# 02 技术选型与架构

> 版本 v0.2（2026-11-06 修订）｜ 状态：已决策 .NET 10 + WPF ｜ 上一版为 Flutter，修订原因见第 2 节

## 1. 结论先行

**C# + .NET 10 (LTS) + WPF，发布为 self-contained 单文件 exe。**
MVP 先出「绿色单文件」：一个 `.exe`，双击即用，不装运行时、不写注册表、不要管理员权限；后续再出 Inno Setup 安装包。

## 2. 为什么从 Flutter 改到 .NET WPF

上一版的结论（Flutter）是按"写代码 + 维护最简单"算的，那时对交付形态的假设是可以接受"exe + 一堆 dll 的文件夹"。你补了三条新约束后，权重变了：

1. **绿色单文件是首要形态**。Flutter 的 Windows 产物天生是 `fvhelper.exe + flutter_windows.dll + data\` 一个目录，要凑成"单文件"只能套 7z SFX 自解压壳——而这正是杀软重点观察的形态，且每次启动要先解压（首启慢 1–2 秒、临时目录留垃圾）。这条把 Flutter 的最大优势（开发快）压到了劣势之下。
2. **自己提交 + 写元数据**成了核心功能，意味着对"原子写、文件锁、长路径、崩溃一致性"的要求变高。WPF/.NET 的 `FileStream`、`File.Replace`、`FileSystemWatcher`、`FileShare` 全是原生 API，处理这些 Windows 细节比 Dart 更直接。
3. **没有既存的 `.dat` 格式要兼容**，格式由我们定，少了一层历史包袱，谁来实现都不受约束——那就按"单文件 + 维护性"选。

而且环境成本反而**降了**：Flutter 要装 3–5GB 的 VS C++ 工作负载；.NET 只要一个 ~300MB 的 SDK，`dotnet build` / `dotnet publish` 全命令行完成，不需要 Visual Studio。

## 3. 三方案在"绿色单文件"约束下的对比

| 维度（权重） | **.NET 10 + WPF（选定）** | Flutter Windows | C# WinForms + .NET Framework 4.8.1 |
|---|---|---|---|
| 绿色单文件可行性（0.25） | **1**：官方 `PublishSingleFile` 直接出一个 exe，不是自解压壳 | 3：只能 SFX 自解压，杀软风险 + 首启慢 | **1**：天然单 exe |
| 单文件体积（0.15） | 3：自包含压缩后约 60–80MB（**待实测**） | 3：40–80MB | **1**：约 1MB |
| 界面能力/观感（0.20） | **1**：XAML + 样式 + 数据绑定，接近 Flutter 的可控度 | **1**：Widget 组合最灵活 | 4：控件原始，好看全靠自绘 |
| 你的上手/维护成本（0.20） | 2：C# 新语言，但 XAML/MVVM 概念与 Flutter 的 Widget/状态管理同构 | **1**：Dart 已熟练 + 热重载 | 3：新语言，且框架已冻结（无新特性、无热重载） |
| 文件系统能力（0.15） | **1**：原子替换、文件共享模式、长路径、监听都是原生 API | 2：`dart:io` 够用，但原子替换/长路径要自己绕 | 1：同上 |
| 环境前置（0.05） | 2：装 .NET 10 SDK，约 300MB | 4：装 VS C++ 工作负载，3–5GB | 2：装 SDK；或零安装但只能写 C# 5 |
| **加权合计（越小越好）** | **≈1.7** | ≈2.2 | ≈2.35 |

**选定理由（一句话版）**：在"必须是单个 exe"这条硬约束下，WPF 是唯一同时满足"真单文件、不装运行时、界面能做得像样、框架还在演进"的方案；体积是它唯一的让步（60–80MB），而 WinForms 省下的 60MB 换来的是自绘 UI 的长期负担和冻结的框架，不划算。

### 被否方案与回退触发条件

| 方案 | 什么情况下回退到它 |
|---|---|
| C# WinForms + .NET Framework 4.8.1 | 若实测单文件体积 > 100MB 且你**坚决**不接受（要求 ≤ 5MB 级），退这个：体积 1MB、零运行时。代价：UI 自绘、框架冻结 |
| Flutter Windows | 若你后面判断"界面好看 > 单文件"，且能接受绿色版=解压后的文件夹（或 SFX）。那你已有的 Dart 技能会让开发最快，引擎设计可平移 |
| Tauri | 若体积要求 ≤ 15MB 且能接受 WebView2 依赖（Win11 自带，老 Win10 可能没有） |

## 5. 工程结构

```
E:\FileEditVersionHelper\app\
├─ FvHelper.sln
├─ Directory.Build.props        统一 LangVersion / 版本号 / 分析器开关
├─ src\
│  ├─ FvHelper.Core\            纯 .NET 类库：模型、编解码、内容库、扫描、提交、导出
│  ├─ FvHelper.Desktop\         WPF：View(XAML) / ViewModel / 平台服务
│  └─ FvHelper.Cli\             命令行入口：无 UI 也能跑通全流程（自测与自动验收用）
├─ tests\
│  └─ FvHelper.Core.Tests\      xUnit：编解码往返、损坏恢复、变更识别、导出逐字节比对
└─ resources\                  图标、字体（若需内嵌）
```

**硬规则**：`FvHelper.Core` 不许引用任何 UI 程序集；它必须能被 `FvHelper.Cli` 独立驱动。这样引擎可单测、可移植（将来换 UI 或上其他平台只换外壳）。

### 依赖（越小越好）

| 依赖 | 用途 | 必需 |
|---|---|---|
| `System.Text.Json`（框架内置） | 索引 JSON 序列化 | 是 |
| `System.Security.Cryptography`（内置） | SHA-256 内容哈希 | 是 |
| `CommunityToolkit.Mvvm` | `ObservableObject`、`RelayCommand`，省掉手写样板 | 是（P3 引入） |
| `xunit` + `xunit.runner.visualstudio` | 测试 | 是（仅测试项目） |
| 第三方 UI 库（MahApps / HandyControl） | 主题控件 | **否**，先自己写样式，真做不动再引 |
| 日志库（Serilog） | 结构化日志 | 否，先用自写轻量日志（写 `%LOCALAPPDATA%\FVHelper\logs`） |

不引 Newtonsoft（`System.Text.Json` 够用）；不引 SQLite（索引就在 `.dat` 里）；不引 ORM。

## 6. 关键流程

**打开目录（读）**
```
选择目录 → 找 .fvhelper.dat
 ├─ 不存在 → "未初始化"引导（初始化 = 写 .dat + .fvhelper\ + rev1 提交）
 ├─ 存在 → 校验魔数/长度/尾魔数/SHA-256
 │    ├─ 通过 → 反序列化 → changelist 列表
 │    └─ 失败 → 试 .fvhelper.dat.bak → 成功提示"已从备份恢复" → 都失败进只读模式
 └─ 只读模式：可浏览/导出，提交与维护按钮禁用并说明原因
```

**提交（写）**
```
扫描（跳过 .fvhelper\ 与忽略规则）→ 与 HEAD 全量树比对（size+mtime 快筛，必要时算哈希）
→ 变更候选（A/M/D/R）→ 用户勾选 + 填说明 + 作者（默认取设置）
→ 逐文件流式哈希写入 objects（已存在则跳过）
→ 构造 Commit（rev=head+1，parentRev=head，全量 tree）
→ 写 .dat.tmp → 回读校验 → 备份旧文件为 .bak → File.Replace 原子替换
→ 刷新列表并定位到新版本
```

**导出（读 + 写目标目录）**
```
读该 commit 的 tree → 校验每个 blob（缺一即中止，不产出半套）
→ 目标目录非空 → 自动建 导出_<工程>_rev<N>_<时间戳>\
→ 按相对路径还原（不覆盖只读文件，冲突改名并记日志）
→ 可选附带 .dat + 该版本引用的 objects（完整历史 / 作为新起点）
→ 完成页：文件数、总大小、目标路径、打开目录
```

## 7. 关键 Windows 细节（本方案的强项，必须做对）

| 点 | 做法 |
|---|---|
| 原子写索引 | `File.Replace(tmp, target, bak, ignoreMetadataErrors: true)`；目标不存在时先 `File.Move`。回读校验放在替换之前 |
| 读被占用的文件 | `new FileStream(path, FileMode.Open, FileAccess.Read, FileShare.ReadWrite \| FileShare.Delete)` —— Word 打开 docx 时也能读 |
| 忽略 Office 锁文件 | 规则 `~$*`（Word/Excel 打开时生成） |
| 长路径 | `app.manifest` 声明 `longPathAware`（保留）。**P1 实测：319 字符路径读写/`File.Replace`/删树全部 OK，本机 `LongPathsEnabled=0` 也不影响（.NET 10 内部自动处理）→ 不做 `\\?\` 前缀拼接**；`SafePath` 只做规范化与越界拦截 |
| 高 DPI | manifest 设 `PerMonitorV2`；WPF 默认 device-independent，需在 125%/150% 下目视验收 |
| 目录监听 | 用 `FileSystemWatcher`（递归、只订阅 Change/Delete/Rename），防抖 1s；MVP 也可以只做"切回窗口时刷新"（更稳） |
| 单文件发布 | `dotnet publish ... --self-contained true -p:PublishSingleFile=true -p:IncludeNativeLibrariesForSelfExtract=true -p:EnableCompressionInSingleFile=true`；首启会把原生库解到 `%TEMP%\.net\`，第二次起变快 |

## 8. 状态、错误与测试

- **状态管理**：ViewModel + `ObservableObject`，页面状态显式建模 `Loading / Empty / Ready / ReadOnly / Error` 五态，UI 每个状态都有对应视图（避免"转圈转到永远"）。
- **错误模型**：`FvhError { Code, UserMessage, ActionHint, Detail }`；UI 只显示 `UserMessage + ActionHint`，`Detail` 落日志。阻断/警示/提示三级见 `phases\P3-桌面界面\README.md`。
- **测试**：`FvHelper.Core` 单测覆盖 ≥ 80%；集成测试在 `%TEMP%\fvhelper-test\` 造 3 个版本 → 导出 → 逐字节比对；`FvHelper.Cli` 作为可脚本化的验收入口（P5 的 A1–A10 里能自动化的一律走 CLI）。
- **门禁**：`dotnet build -warnaserror` 零警告、`dotnet test` 全绿。

## 9. 构建与交付

```powershell
# 开发运行
dotnet run --project app\src\FvHelper.Desktop
# MVP 绿色单文件
dotnet publish app\src\FvHelper.Desktop -c Release -r win-x64 --self-contained true `
  -p:PublishSingleFile=true -p:IncludeNativeLibrariesForSelfExtract=true `
  -p:EnableCompressionInSingleFile=true -p:DebugType=None
# 产物：app\src\FvHelper.Desktop\bin\Release\net10.0-windows\win-x64\publish\FvHelper.exe（单文件）
```
- 体积：**P1 实测 58.83 MB**，发布目录只有 1 个 `FvHelper.exe`；首启 1330 ms（原生库解到 `%TEMP%\.net\`）、二启 692 ms。远低于 100MB 回退线，**不启用 WinForms 回退**。
- 后续安装包：Inno Setup（`tools\打包\fvhelper.iss`），输出 `releases\FVHelper-Setup-<ver>.exe`。
- 版本号集中在 `Directory.Build.props`，界面"关于"页与产物文件名同源。
