# 03 数据格式规范 v0.1（`.fvhelper.dat` 与内容库）

> 本文件是格式的唯一准绳：**先改这里，再改代码**。任何字段增删都要升 `formatVersion`。

## 1. 目录布局

一个论文工程（用户打开的目录）在版本化之后长这样：

```
F:\论文\
├─ 论文正文.docx              ← 用户文件（工作区）
├─ 参考文献\
│  └─ 综述.pdf
├─ .fvhelper.dat             ← 数据信息文件（版本索引，唯一入口；默认 Hidden）
├─ .fvhelper.dat.bak         ← 上一次完好索引的备份（同样 Hidden）
└─ .fvhelper\                ← 内容库（工具私有，扫描时整体忽略；目录 Hidden）
   └─ objects\
      ├─ ab\abcd1234...ef     ← 一个文件的完整内容，文件名 = SHA-256
      └─ 7f\7f00aa...12
```

设计取舍：
- **只用两个入口**（`.fvhelper.dat` + `.fvhelper\`）。用户拷目录、压缩打包不会漏；工具不需要任何全局数据库。
- **内容按哈希存**，同一文件多版本只存一份差异内容，天然去重；论文场景（docx 每版几 MB）空间占用可控。
- `.fvhelper\` 与 `.fvhelper.dat*` 一律进忽略规则，绝不出现在 changelist 里。
- **对用户不可见**（P4 口径）：`.fvhelper.dat` / `.bak` / `.tmp` 与 `.fvhelper\` 写完就统一打 Windows `Hidden` 属性，资源管理器（默认设置）里看不到，用户只看到自己的文件。只有属性、不改内容；属性改失败（只读介质、非 NTFS）静默跳过、不影响读写。打开项目时也会补打一次（老版本建的库升级后即被隐藏）。
  - 注意 Windows 的 `CREATE_ALWAYS` 语义：带 `Hidden` 的文件不能直接被 `File.WriteAllBytes` 覆盖（会 ACCESS_DENIED）。所以写路径一律走 `.tmp + File.Replace`（`DeepCopyAttributes` 之后重新 `Hide`），维护脚本要整文件重写时先清 `Hidden`（`FvHelper.Core.VersionData.Unhide`）。

## 2. 二进制容器

```
偏移    长度   内容
0       4      魔数 "FVH1"（ASCII）
4       2      formatVersion，uint16 LE，当前 = 1
6       2      flags，uint16 LE：bit0=payload 为 gzip；bit1=含 payload 校验和（当前固定置 1）
8       4      payloadLength，uint32 LE（压缩后的长度）
12      N      payload：JSON（UTF-8），gzip 压缩
12+N    32     SHA-256(payload 原始解压后字节)
12+N+32 4      尾魔数 "END!"（ASCII）
```

规则：
- 读取时**先校验魔数、长度、尾魔数、SHA-256**，任一不符按"损坏"处理，转 `.bak` 恢复流程。
- 未来版本：`formatVersion` 不同则走迁移器（`MigrationV1toV2` 等），旧版工具读新版文件时提示"请升级程序"，不得静默写坏。
- 调试需求：设置里提供"导出明文索引 JSON"（仅读取，不参与运行），便于排错与人工审查。

## 3. 索引 JSON（schema = `fvhelper.index/1`）

```json
{
  "schema": "fvhelper.index/1",
  "repoId": "9f2c1e7a-...",
  "createdAt": "2026-11-06T14:00:00+08:00",
  "appVersion": "0.3.0",
  "head": 3,
  "author": "黎广",
  "ignore": [".fvhelper/**", ".fvhelper.dat*", "~$*", "*.tmp", "Thumbs.db", "desktop.ini"],
  "commits": [
    {
      "rev": 3,
      "id": "a1b2c3d4",
      "parentRev": 2,
      "message": "按导师意见改结论与图表编号",
      "detail": "改了第四、五章结论；图表编号统一为 图3-1 形式；导师意见已逐条回复。",
      "author": "黎广",
      "createdAt": "2026-11-06T15:32:10+08:00",
      "stats": { "files": 12, "added": 1, "modified": 2, "deleted": 0, "renamed": 1, "bytes": 8342110 },
      "changes": [
        { "path": "论文正文.docx", "action": "M", "hash": "sha256:8c1f...", "size": 2519040, "mtime": "2026-11-06T15:30:00+08:00" },
        { "path": "图\第三章-流程图.png", "action": "A", "hash": "sha256:44ba...", "size": 812340 },
        { "path": "旧稿\绪论-废弃.docx", "action": "D", "oldHash": "sha256:77e0..." },
        { "path": "附录A 数据表.xlsx", "action": "R", "from": "数据表.xlsx", "hash": "sha256:0f9c...", "size": 40211 }
      ],
      "tree": [
        { "path": "论文正文.docx", "hash": "sha256:8c1f...", "size": 2519040 },
        { "path": "图\第三章-流程图.png", "hash": "sha256:44ba...", "size": 812340 },
        { "path": "附录A 数据表.xlsx", "hash": "sha256:0f9c...", "size": 40211 },
        { "path": "参考文献\综述.pdf", "hash": "sha256:1122...", "size": 3120000 }
      ]
    }
  ]
}
```

字段说明：

| 字段 | 类型 | 说明 |
|---|---|---|
| `repoId` | string | 仓库 UUID，导出"作为新起点"时重新生成 |
| `head` | int | 当前最新 rev；0 表示空仓库 |
| `author` | string | 默认作者名（设置可改，提交时写入快照） |
| `ignore` | string[] | 忽略规则（glob，相对仓库根），写入索引以便换机后行为一致 |
| `commits[].rev` | int | 版本号，从 1 连续递增，不复用 |
| `commits[].id` | string(8) | 展示用短 id（由 rev+message+时间哈希得出，只做展示与分享） |
| `commits[].parentRev` | int | 父版本；rev1 为 0 |
| `commits[].message` | string | 提交**标题**（一行，界面底部的输入框） |
| `commits[].detail` | string | 提交**详情**（多行，可空；2026-11-06 新增，旧库缺这个字段时读出来是空串，不影响向上兼容） |
| `commits[].changes[].action` | "A"/"M"/"D"/"R" | 新增/修改/删除/重命名 |
| `changes[].hash` | string | `sha256:<64 hex>`，指向 objects 里的 blob；D 动作无此字段 |
| `changes[].oldHash` | string | 仅 D/R 有，记录被删/被改名的旧内容，便于恢复 |
| `tree` | array | **该版本的全量文件清单**（不含 `.fvhelper*`），导出直接用它 |

### 3.1 为什么每次存全量 tree

- 论文目录文件数少（典型 20~200 个，极端 1000 个），100 个版本的全量 tree 压缩后通常 < 1MB，可以接受。
- 导出/展示**不需要回放历史**，少一整类 bug（回放顺序错、中间版本树算错）。
- 触发重构的条件：单仓库 `tree` 条目总数 > 50 万或 `.dat` 压缩后 > 20MB → 改为"增量 + 每 20 版存 keyframe"（届时升 formatVersion）。

## 4. 内容库（blob）规范

- 路径：`.fvhelper\objects\<hash前2位>\<hash后62位>`，全小写 hex。
- 内容：**原文件的完整字节**，不做压缩（docx/pdf 本身已压缩，二次压缩收益低且增加 CPU）；后续可选 zlib 分支，需在 blob 头加标识（当前不加，保持简单）。
- 写入：先写 `objects\tmp\<uuid>.part` → 校验哈希 → 改名为最终路径（同盘 rename 原子）。
- 已存在同名 blob → 直接跳过（内容寻址天然幂等）。
- 只读打开的场景不写任何 blob。

## 5. 原子写与崩溃恢复

写索引的顺序（顺序错了就会丢历史）：

```
1. 写全部新 blob 并校验
2. 写 .fvhelper.dat.tmp（完整容器字节）
3. 重新读取 .tmp 并校验（魔数/长度/尾魔数/SHA-256）
4. 若 .fvhelper.dat 存在 → File.Copy 到 .fvhelper.dat.bak（覆盖）
5. File.rename(.tmp → .fvhelper.dat)，失败则重试 3 次后报错
6. 刷新 UI
```

- 进程在 1~4 之间被杀：索引仍是旧的，孤儿 blob 由"清理未引用 blob"回收，**无数据损失**。
- 进程在 5 中被杀：可能出现 `.fvhelper.dat` 缺失或截断 → 启动时检测到就自动用 `.bak` 恢复，并提示。
- 任何情况下**不得**直接写入 `.fvhelper.dat` 本体。

## 6. 兼容与只读模式

- 允许打开"非本工具生成但符合本规范"的 `.dat`；若 `formatVersion` 更高 → 只读 + 提示升级。
- `schema` 字符串不认识 → 只读降级，UI 上明确标注"只读：数据格式不受支持"。
- 只读模式下所有写路径（提交/清理/迁移）禁用，导出仍可用。

## 7. 导出规范（两种模式）

### 7.1 仅文件（默认，交稿用）

```
<目标>\导出_<工程名>_rev<N>_<yyyyMMdd-HHmmss>_仅文件\
  论文正文.docx
  图\...           ← 完全按 tree 的 paths 还原
```
- 不含任何 `.fvhelper*`；不覆盖用户已有文件（目标非空则新建子目录）。
- 还原前校验每个 blob 的哈希，任一缺失/不匹配 → 中止，不产出半套文件（避免导师收到残缺稿）。
- **目录名自带"含不含版本信息"（P4）**：`_仅文件` / `_含版本信息` / `_含版本信息-新起点`。攒了几个导出目录时，光看名字就能分清哪个能继续提交、哪个只是当版文件。

### 7.2 文件 + 数据信息文件（备份/换机用；界面文案"导出（含版本信息）"）

- 复制 `.fvhelper.dat`（可选项：保留完整历史 / 裁剪到该版本）。
- 复制 `.fvhelper\objects\` 中**该版本被引用到的 blob**（不整库复制，避免把 3GB 历史全带走）。
- 默认策略：**保留完整历史**（换机后仍能看到全部提交记录并继续提交）；勾选"作为新起点"时：
  - 新建 `repoId`，只保留该 rev 的 tree 作为 rev1（message = `从 rev<N> 导出`），其余历史丢弃、objects 按需精简。
  - **该 rev1 的 `changes` 全部重写为 `A`**（因为对新仓库来说这些文件都是第一次出现；照搬原提交的 M/D/R 会自相矛盾）。P2 已按此实现并加测试。
- 导出的 `.fvhelper.dat` / `.fvhelper\` 同样打 `Hidden`：对方打开导出目录只看到文件本身，不知道版本信息在哪一层，也就不会误删。

### 7.3 本地加速缓存（P2 新增，不属于历史数据）

`.fvhelper\state.json`：记录每个文件上次提交时的 `(size, mtimeTicks, hash)`。
- 用途：扫描时若 `size + mtime` 与缓存一致且缓存哈希等于 head tree 的哈希，就**跳过重新哈希**（1001 文件实测 752 ms → 324 ms）。
- 它不是历史数据、不进 `.dat`、不参与任何校验层；删掉只影响下一次扫描速度。
- 部分提交后，**只缓存"工作区内容确实等于新提交树"的文件**，否则未提交的改动会被误判为"无变化"。

## 8. 路径安全（必须实现，防手滑与防恶意文件）

- `path` 字段一律为**相对路径**，正斜杠 `/` 存储，还原时按平台分隔符拼接。
- 读取与还原时逐条校验：不含 `..` 段、不以 `/` 或盘符开头、不包含 Windows 保留字符、长度合规；违规条目直接拒绝并记日志（防 zip-slip 类目录穿越）。
- 还原时不跟随符号链接/联接（junction），遇到则跳过并提示。

## 9. 文件与数据匹配校验（FR-15 实现口径）

"文件与数据是否匹配"要分四层校验，每层结论独立呈现，**绝不静默放过**。

### 9.1 四层校验

| 层 | 名称 | 校验内容 | 触发时机 | 失败含义 |
|---|---|---|---|---|
| L1 | 容器完整性 | 魔数 `FVH1`、`formatVersion`、`payloadLength`、尾魔数 `END!`、payload 解压后 SHA-256 | 每次打开项目 | `.dat` 被截断/改坏 → **损坏** |
| L2 | 索引自洽 | `schema` 可识别；`head` == `commits` 最大 rev；`parentRev` 链完整（rev N 的父存在）；每条 `tree[].path` 唯一且全部通过路径安全校验；`changes` 与"父 tree → 本 tree"差集一致（动作类型对得上） | 每次打开项目 | 数据自相矛盾（被外部工具篡改/写入中断）→ **不匹配** |
| L3 | blob 存在性与内容一致 | ①**全部历史提交**引用到的 hash 在 `.fvhelper\objects\` 中存在且大小 == `tree[].size`（不只是 head：完整历史导出要用旧版本内容）；②（按需重算）文件字节的 SHA-256 == 文件名/hash 字段 | ①打开项目时（只查存在性+大小，快）；②**导出前必做全量重算**；③设置里"校验完整性"可手动全量 | 内容库缺文件或内容被替 → **不匹配** |
| L4 | 工作区一致性 | `head` 的 `tree[]` 与磁盘现状比对：路径是否存在、大小/mtime、可选哈希 → 产出"改动清单" | 扫描（显式点"重新扫描"或选中项目时） | **不是错误**：这正是"检测到 N 个文件有改动"的数据来源 |

### 9.2 结论等级与 UI 呈现

| 等级 | 条件 | UI | 允许的操作 |
|---|---|---|---|
| `OK` | L1/L2/L3(存在性) 通过，L4 无改动 | 淡绿条"✓ 已校验：该版本记录的文件与版本信息一致（文件数、哈希全部匹配）" | 全部可用 |
| `WARN` | L1~L3 通过，L4 有改动 | 淡黄条"检测到 N 个文件有改动（修改 X/新增 Y/删除 Z）——是否提交为新版本？" | 提交/导出/查看 |
| `MISMATCH` | L2 或 L3 失败 | 红条 + 明细："索引记录 12 个文件，其中 2 个内容库缺失：`图\第三章-流程图.png`、`参考文献\综述.pdf`" | **禁止导出与提交**，允许浏览历史与只读打开工作区文件 |
| `CORRUPT` | L1 失败 | 红条 + 引导："版本信息损坏（版本信息文件读不出来），已禁止提交与导出" | 恢复成功后重跑 L1~L3；恢复失败 → 只读 + 建议联系对方重发 |
| `OK` + `isNewRepo` | **全新文件夹**：`.fvhelper.dat` 与 `.bak` 都不存在 | 灰条"· 这是全新文件夹：还没有版本信息，第一次提交时自动建立（现在没有可校验的版本记录）" | 提交（首次提交即建库，rev 1）／导出暂不可用 |

> **2026-11-06 修正（调试问题）**：以前"没有 `.fvhelper.dat`"一律按 L1 `CORRUPT` 处理，导致**新建/添加一个空文件夹就跳出红条"版本信息损坏"并禁掉提交**（D-13 的禁令把新用户挡在门外）。现在 L1 先区分三种情况：①文件不存在且没有 `.bak` → `IsNewRepo`（上面最后一行）；②文件在但读不出/结构不对 → 真 `CORRUPT`（走 `.bak` 恢复引导）；③文件不在但有 `.bak` → 仍按 `CORRUPT` 并提示可用备份恢复。用例见 `ExportAndVerifyTests.全新文件夹不算损坏而是可以开始用`。

### 9.3 实现要点

- **导出前必须全量重算** L3②，任一 blob 缺失或哈希不符 → **中止导出、不产出半套文件**（避免导师收到残缺稿）。哈希吞吐按 P1-V4 实测 ~214MB/s（100MB 单文件 468ms），2GB 目录约 10s，走后台线程 + 进度条 + 可取消。
  - **P2 实现补充**：预校验在**写任何文件之前**完成；若中途仍失败，会删掉本次新建的导出目录（不留半套）。
- 打开项目时的 L3 只做"存在性 + 大小"，避免每次打开都全量读盘；`size` 不符即判 `MISMATCH`（比哈希更便宜的第一道筛子）。
- **提交前也跑 L1–L3**（P2 实现，D-13）：数据与内容不自洽时直接拒绝提交，不把坏状态继续往前推。
- L4 的哈希比对默认用 `(size, mtime)` 快速筛（P2 用 `.fvhelper\state.json` 缓存实现，见 §7.3），仅当 `size/mtime` 变了才真算哈希；这样"只打开没保存"不会被算成修改。
- 校验结果同时写日志（`%LOCALAPPDATA%\FVHelper\logs`），便于"对方发来的包为什么打不开"这类问题定位。
- **导出包被他人继续使用**的语义：带数据信息文件的导出包 = 一个完整可续作的仓库副本（`repoId` 相同、历史相同）。对方提交后 `repoId` 仍相同、rev 继续增长；两份分叉副本不会自动合并（v1.0 不做合并，遇到 `repoId` 相同但 head 不同的情况在 UI 上提示"这是同一仓库的另一个副本，提交将在本机副本上继续"）。

## 10. 待定项

| 编号 | 待定 | 倾向 |
|---|---|---|
| F-01 | blob 是否压缩 | 暂不压缩，v1.1 评估 |
| F-02 | 是否记录行级文本差异 | v1.1，docx 需解压 `word/document.xml` 比对文本 |
| F-03 | `.dat` 是否加密 | 不做（学生论文无保密需求，加密会带来密码丢失=历史全丢的坑） |
| F-04 | 大文件阈值 | 默认不跳过；设置里可设"跳过 > N MB 的文件"，默认关闭 |
